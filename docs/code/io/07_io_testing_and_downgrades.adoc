// --- Sub-Assembly 3.1: Standardized Test Band Architecture ---
== Crude-to-Fine Band Design

Every CTest suite in `io/` executes through the shared `tests/common/cornerstone_test.h` harness (`test.common.harness`), partitioning assertions into progressively tighter assurance bands:

[cols="2,4",options="header"]
|===
| Band | Verification Question Answered

| `always_pass`
| Can `io_init()` / `io_fallback_boot()` initialize safely from clean `.bss` without crashing or touching the heap?

| `never_fail`
| Do oversized payloads (`> 65536` B), NULL buffers, `..` traversal attempts, and invalid `block_3_body` spans return safe typed errors instead of faulting?

| `assertions_and_guarantees`
| Do disk overrides (`game/config`) outrank `engine/config`, and do missing files increment `rom_loads` with `loaded_from_rom = true` identically?

| `emergence`
| When chained across real subsystem boundaries, do VFS lookup, 5-block JSON parsing, logging, and probe triggers compose cleanly without state leaks?

| `preflight_audit` / `audit`
| Do `io_preflight()`, `io_audit()`, and `master_loader_audit()` pass cleanly with deterministic post-run counters and clean teardown?
|===

// --- Sub-Assembly 4.1: Running Targeted I/O Tests ---
== Running & Auditing the `io/` Test Suite

[source,bash]
------
cmake -B build && cmake --build build -j
ctest --test-dir build \
  -R "(fs_utils|path_finder|json_utils|master_loader|io_fallback|_io_)" --output-on-failure
------

If any `io/` probe fires unexpectedly during a run, `tests/common/cornerstone_test.h` prints the forensic `debug` / `debug_fallback` ring snapshot and pinpoints the exact test file, band, and `DEBUG_STEP_AWAIT` code.
