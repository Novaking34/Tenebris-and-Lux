== Abstract & Engineering Intent

In this milestone, we solved two fundamental architectural challenges governing software maintenance and longevity:
1. **The Pedagogical Metadata Dilemma**: How to structure source file metadata so that a novice programmer never feels overwhelmed or lost, while an experienced systems architect never feels patronized or deprived of rigorous technical contracts.
2. **Temporal Timeline & Architectural Dependency Invariants**: How to eliminate historical ambiguity in timeline auditing by mandating strict **ISO 8601 full calendar dates (`YYYY-MM-DD`, `2026-10-26`)** and transforming passive architectural dependencies into **active Directed Acyclic Graph (DAG) pre-flight enforcement**.

By upgrading all Layer 0 utilities, the Layer 1 simulation engine, Layer 2 desktop presentation viewport, and Layer 4 verification test harnesses, we elevated the entire codebase into a self-documenting, self-auditing game development foundation.

---

== 1. The Pedagogical Balancing Act: Beginner Mission vs. Senior Contracts

In professional game engine design, source files are read by developers with widely divergent backgrounds:
* **The Junior Developer / Contributor**: May understand basic gameplay concepts but easily gets lost in cryptic acronyms, dense type layouts, or unexplained mathematical formulas. If a header only contains bare function signatures without context, they do not understand *why* the module exists or what breaks if they alter a value.
* **The Senior Systems Engineer / Architect**: Needs instant, unambiguous answers regarding memory allocations (heap vs. stack), concurrency reentrancy, cache latency budgets, interface ABI stability, and upstream prerequisites. If a file contains verbose narrative hand-waving without concrete invariants, they cannot verify safety guarantees or integration boundaries.

=== 1.1 The Dual-Audience Protocol

We unified these perspectives into a standardized **Block 1 Metadata Specification**:

[source,c]
----
// =============================================================================
// BLOCK 1: METADATA BLOCK
// ( Identity, Provenance, Invariant Boundary Contracts & System Anchors )
// =============================================================================
// @project       Tenebris and Lux
// @file          time_utils.h
// @id            core.util.time
// @layer         Layer 0: Core Utilities
// @version       1.0.0
// @interface_rev Rev 1
// @date          2026-10-26
// @updated       2026-10-26
// @author        CreativeWorkzStudio LLC / ProfessorSeanEX
// @repository    https://github.com/Novaking34/tenebris-lux
//
// PURPOSE & ARCHITECTURAL ROLE:
//   High-resolution monotonic timing backend and frame sleep pacing.
//   Serves as the foundation for elapsed time measurement across simulation
//   ticks and presentation frame pacing (60 FPS latency budget).
//
// DEPENDENCY & RESOURCE CONTRACTS:
//   - Upstream Dependencies: None (Foundational leaf module).
//   - Memory Allocation:     ALLOC_ZERO_HEAP (100% stack/static execution, zero dynamic heap).
//   - Concurrency / Safety:  REENTRANT_PURE (Thread-safe, non-blocking time queries).
//   - Latency Budget:        < 5 microseconds per query.
//
// AXIOMATIC INVARIANTS:
//   1. Monotonicity: Time guarantees strictly non-decreasing clock ticks (t2 >= t1).
//   2. POSIX conformance: CLOCK_MONOTONIC timing source without drift or leap adjustments.
//   3. Frame sleep pacing: Non-negative sleep durations (negative inputs clamped to 0).
// =============================================================================
----

* **For Beginners**: The `PURPOSE & ARCHITECTURAL ROLE` field clearly frames the module's place in the universe using plain English, explaining both its simulation role and what other systems rely upon it.
* **For Seniors**: The `DEPENDENCY & RESOURCE CONTRACTS` and `AXIOMATIC INVARIANTS` fields supply exact, uncompromised technical contracts: zero heap allocation (`ALLOC_ZERO_HEAP`), pure reentrancy (`REENTRANT_PURE`), sub-5-microsecond latency, and mathematical clamping properties.

== 2. Temporal Precision: Mandating Full ISO 8601 Calendar Dates

Prior iterations utilized a compact month-and-year epoch stamp (e.g. `2026.10`). While concise, empirical timeline auditing revealed that month/year stamps obscure chronological sequencing:
1. When multiple architectural refactorings occur across consecutive days within the same month, month-level stamps fail to convey sequence.
2. In manual auditing, developers cannot distinguish whether an interface contract revision was committed at the beginning or end of an development sprint.
3. Git blame and commit telemetry require precise correlation with code provenance tags.

Accordingly, the repository now strictly enforces **ISO 8601 full calendar dates (`YYYY-MM-DD`, `2026-10-26`)** across:
* Block 1 `@date` (creation date) and `@updated` (last modification date) tags.
* Compiled `module_metadata_t.last_updated` string constants.
* Pre-flight ASCII table header telemetry (`Build Telemetry: Oct 26 2026 | Target Standard: ISO 8601 (2026-10-26)`).
* All technical architecture specifications and dev logs.

== 3. Active DAG Dependency Contracts: Turning Comments into Machine Tripwires

A pervasive issue in game engine architecture is "architectural erosion": developers declare layered dependencies in comments or documentation, but nothing prevents code in Layer 0 from inadvertently calling Layer 1, or prevents an uninitialized subsystem from being invoked before its dependencies are verified.

We elevated dependencies from passive comments into an **Active Directed Acyclic Graph (DAG)** validated at boot time.

=== 3.1 Compiled 5-Dimension Metadata Schema

In `include/util/manifest.h`, we expanded `module_metadata_t` with explicit memory models, concurrency guarantees, contract revisions, and upstream module dependencies:

[source,c]
----
typedef enum {
    ALLOC_ZERO_HEAP = 0,    // Pure stack/static execution (Layer 0 guarantee)
    ALLOC_FIXED_POOL,       // Fixed static ring/pool buffers
    ALLOC_ARENA,            // Frame/scene arena allocator
    ALLOC_DYNAMIC           // Managed heap allocation
} alloc_policy_t;

typedef enum {
    CONCURRENCY_REENTRANT = 0, // Thread-safe, stateless pure functions
    CONCURRENCY_THREAD_LOCAL,  // Per-thread state
    CONCURRENCY_MAIN_THREAD    // Viewport/GUI event loop affinity
} concurrency_policy_t;

typedef struct {
    /* 1. Identity & Provenance */
    const char *module_id;          // e.g. "sim.engine.core"
    const char *file_name;          // e.g. "game.h"
    module_layer_t layer;           // Stratum in architectural hierarchy
    struct {
        uint8_t major;
        uint8_t minor;
        uint8_t patch;
    } version;
    uint8_t interface_rev;          // Contract ABI revision
    const char *last_updated;       // ISO 8601 full date: "YYYY-MM-DD"
    const char *description;        // Plain-English mission statement
    
    /* 2. Architectural Dependencies */
    size_t dependency_count;
    const char *dependencies[MANIFEST_MAX_DEPENDENCIES]; // Upstream module IDs required
    
    /* 3. Resource & Execution Contracts */
    alloc_policy_t alloc_policy;
    concurrency_policy_t concurrency;
    uint32_t max_budget_us;         // Max execution latency budget (in microseconds)
    
    /* 4. Invariant Contracts */
    size_t invariant_count;
    const char *invariants[MANIFEST_MAX_INVARIANTS];
    
    /* 5. Pre-Flight Machine Self-Audit */
    diag_result_t (*preflight_check)(void);
} module_metadata_t;
----

=== 3.2 Pre-Flight DAG Enforcement Algorithm

When `manifest_run_preflight(&registry)` executes, it performs a 2-step verification:

```text
┌─────────────────────────────────────────────────────────────┐
│ STEP 1: Upstream DAG Dependency Graph Validation            │
│ For each registered module:                                 │
│   For each declared dependency in dependencies[]:           │
│     Verify upstream module_id is registered in manifest.    │
│     If missing -> Flag SEVERITY_FATAL, HALT BOOT IMMEDIATELY│
└──────────────────────────────┬──────────────────────────────┘
                               │ (All Upstream Dependencies Satisfied)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ STEP 2: Functional Loose-Bolts Subsystem Pre-Flight Checks  │
│ Execute preflight_check() function pointer per module.      │
│ Apply graded policy escalation:                             │
│   PASS -> OK | WARN -> Warnings | CRIT -> Downgrade | FATAL │
└─────────────────────────────────────────────────────────────┘
```

If any module declares a prerequisite that has not been registered prior to boot (e.g. `sim.engine.core` declaring `core.util.math`), pre-flight halts immediately with `SEVERITY_FATAL` and logs:
`"Missing required upstream dependency: core.util.math"`.
